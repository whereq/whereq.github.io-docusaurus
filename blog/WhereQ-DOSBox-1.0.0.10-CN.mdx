## 那段留在后面的音乐

你在 boss 打到一半的时候按了存档。音乐正响，那只大家伙正在做一件让人难受的事，你把手机放下，去回一条消息。

两分钟后你回来，读档。

战斗和你离开时一模一样——怪物、血条、它的坐标，样样都对。可音乐完全不在同一条时间线上：它从来没有跟机器一起被冻住，于是一切都倒回去了，它还在往前放。而 PC 喇叭那头的哔哔声还在后台嗡嗡地响，谁也不理。

那是 1.0.0.9。存档做得很好，好到只差一样东西：声音。

## 存档存的是一台机器，不是一块屏幕

存档本来应该存下整台机器：CPU、内存、显存、打开的 DOS 文件句柄、硬件定时器。少了机器的任何一个部件，读回来就只是一台略有不同的机器——而这一次，你听得出来。

FM 芯片根本不在快照里。不是存得不准、不是存得不全——是压根没有。

这比听上去更糟，因为游戏冻住的时候芯片并不会跟着停。游戏运行中读档，模拟器会把它知道的一切倒回去：怪物、血条、那只大家伙的坐标、DOS 文件句柄、定时器。芯片不在它知道的那一串里，于是它继续放下去。你眼前是一场被倒带的战斗，耳朵里却是没有倒带的音乐。

如果这份存档是被恢复进一个全新的进程里——也就是关掉应用之后再按**继续**时发生的事——那芯片是崭新的、空白、哑的，音乐直接就没了。

PC 喇叭坏得又是第三种方式。它**确实**在快照里，可它是个实时输出设备，它排队的延迟和定时器索引被按着**当前**时钟恢复，而不是被保存时的那台机器的时钟——于是混音器继续发出一个客人根本没要求过的蜂鸣。它带着嗡声回来了。

## 「精确」在这里是什么意思

修法是把芯片本身整个存下来，而不是存它的摘要。OPL 的状态是**一个**大约五千字节的结构体：每个运算单元的包络、波形相位、LFO 计数器、反馈历史。它被写进状态文件、再读回来，于是下一个采样点从上一个采样点停下的地方接着走。

还有一种更省事的做法，值得说清楚它为什么不够用。这个移植留着芯片的 512 个寄存器——驱动把音色写进去的那些——读档时可以重放它们。这能把音色完美地重建出来。但驱动在一首曲子的开头把音色编好，之后只发「按下」和「松开」；在这中间发生的一切都活在**芯片内部**，没有任何一个寄存器记录得了。于是重放寄存器就等于把每一个音符都从攻击段重新触发。音回来了，却回错了：它从头开始，而不是从原来的地方接着走。

所以寄存器重放还在，作为那些无法快照自己的 OPL 模型的兜底。但它现在只是兜底，不再是主方案。

这个测试包就在仓库里，你也可以自己跑。屏幕上就写着它是什么：*"The tone is playing. Press any key to stop it."*

然后这个移植在存档时把芯片的状态打进日志，读档时再打一遍，两边必须对得上——同样的包络、同样的波形相位、同样的 LFO 计数器、同样的寄存器内容。

这是相隔两分钟真实芯片时间的存档日志和读档日志：

```
savestate: OPL chip saved:    ... phase=d96f49ac ... active=36 lfo=000b228c opl3=0
savestate: OPL module saved:  exact=1 mode=2 regs=62/512 r20=31 r23=31 r40=3f ...

savestate: OPL chip restored: ... phase=d96f49ac ... active=36 lfo=000b228c opl3=0
savestate: OPL module restored: exact=1 mode=2 regs=62/512 r20=31 r23=31 r40=3f ...
```

一模一样。音从攻击段中间接上，继续响。

## 有件事你得知道

**1.0.0.9 写下的存档，1.0.0.10 读不了了。**

声音芯片进了快照之后，状态文件多了一个版本号，读档端现在会**拒绝**旧存档，而不是硬把它读错。这才是诚实的做法——一个能读、但声音读错的存档，比一个直接说「不行」的存档更糟糕。

如果你手上有 1.0.0.9 留下的存档在意，升级之前先读出来。

## 一个一直按着的键

按着某个键的时候转屏，那个键会永远按在 DOSBox 里。旋转之后布局要重建，而重建出来的布局没有告诉模拟器「手指已经抬起来了」，于是那个键一直按着，DOSBox 就一直重复它。

现在，布局重建时，所有处于按下状态的键都会被释放。

还有另一半。**Ctrl** 同时出现在两个地方——手柄区和折叠面板上——而代码默认它上面永远只有一根手指，于是在一处松开会把另一处也取消掉。现在它会数手指。

## 塞得下的启动器

**Files** 面板现在会量一量自己有多少空间，再据此限制游戏列表的数量。以前装到第三个游戏，按钮会被挤出面板底边——掉下去就再也捞不回来了。

这是这一版里最小的改动，也是我最恼火它没在前三个版本里就发生的一个。

## 桌面版又能链接了

存档相关的代码从来没被加进 autotools 的构建里，所以那个桌面基线——也就是那个能在笔记本上几秒钟编完、用来盯着模拟器内核别走偏的构建——从 1.0.0.8 引入存档开始就链接不过了。

我为这件事蒙了整整两个版本，因为我忙着发安卓版，一直没顾上。

原因有四条，彼此独立，但其实是同一类：构建里漏了一个源文件、少了一个头文件、一个函数本来该被条件编译掉、以及同一个静态库被连着列了两次——那是一个循环依赖，换个顺序才会暴露。

现在基线又能编译链接，也能跑。

## 一份文档，而不是一本流水账

仓库过去有一个 `porting/` 目录：一份移植日志、一些跑分笔记、一份键盘设计说明，还有一个日志文件。还在写移植的时候它们很有用；写完之后就没用了，因为那是**按时间顺序记下来的东西**——你得先知道事情发生的先后，才知道现在哪一条是真的。

现在只剩**一份**参考文档：[`docs/TECHNICAL-REFERENCE.md`](https://github.com/whereq/whereq-dosbox/blob/main/docs/TECHNICAL-REFERENCE.md)。整个实现都在这一个地方——原生构建和 ABI 矩阵、存档机制和它的文件格式、精确的 FM 快照、快照里的 DOS 层、启动器、屏幕键盘、吞吐跑分、还有哪些东西没被拍进去，以及这个移植拍下的每一张截图，都带着源码引用。

流水账没有消失，它变成了章节。历史仍然在 git log 里，那本来就是历史该待的地方。

## 安卓移植结束了

这一版带了一个不是版本号的标签：

```
milestone/android-migration-complete
```

它是带注释的，曾经指向这一版的提交（这个标记后来移到了 v1.0.0.13），而且**故意**落在发布脚本能理解的 `vX.Y.Z.A` 格式之外，所以脚本永远不会再把它当成一次发布捡起来。

它标记的是一个阶段，不是一个版本。安卓移植已经完成：模拟器核心能为三个 ABI 编译，应用层在真机上跑得动，存档装得下整台机器——包括声音——桌面基线也能链接了。接下来是**维护**：修 bug 和打磨文档。没有新功能的计划。

发布版 APK 就在仓库里，用发布密钥签名，可以直接覆盖安装 1.0.0.9：

```
downloads/whereq-dosbox-1.0.0.10.apk
sha256: 80bdce1b4bdeba809159310441e450e704f6c322e2a3ff98bcc822ed50077018
```

GitHub Release 上另有一份由流水线在干净机器上构建的产物，旁边带着它自己的 SHA-256 文件。

它跑在 **arm64-v8a、armeabi-v7a 和 x86_64** 设备上，要求 Android 5.0 及以上，完全离线，不需要账号，没有任何追踪。项目采用 GPL-2.0 许可，DOSBox 核心连同它的 `AUTHORS`、`ChangeLog`、`COPYING` 和逐文件头注释一起嵌入。

再说一遍：**这篇文章不是文档。** 文档是仓库本身，而且现在是一份参考文档，不再是一堆笔记。请去读那份，而不是信我的一面之词。

**DOSBox** 由 [DOSBox Team](https://www.dosbox.com/crew.php) 写成——一群志愿者把 1994 年的一套操作系统改造到此后世界造出的每一台机器上都能跑，包括那些当时还不存在的机器。他们让它活过了三十年，并免费交给任何想要的人。WhereQ-DOSBox 只是建在他们工作之上的一层薄薄的壳。原创力、手艺和慷慨完全属于他们。
