## The corridor you have already walked

A DOS game does not have an autosave. Some of them have a save file of their own; most do not; the ones that do usually put it somewhere in the current directory and expect you to find your way back through a menu.

So you do what every DOS player did in 1996: you play for forty minutes, you die in a corridor you have already walked twice, and you walk it again. Same door, same guard, same room with the lever you forgot to pull. The game does not know how far you got. Nothing on the phone knows either.

**1.0.0.8** is the release that changed that — not with a better save file, but with a different idea of what to save.

## A save state is the machine, not the game

The thing DOSBox never had, and which no DOS game asked for, is a **save state**: the whole emulated machine, frozen, written to a file and read back later — into a *freshly booted* DOSBox if need be.

Not the game. The machine. The CPU with its registers, the DOS memory, the video memory, the hardware timers, and the DOS file handles the program had open. Everything that made this run *this run, at this instant*. Restore it and you are not near where you were: you are there.

DOSBox r4305 has no save states at all, so I wrote one into the port. Every game gets **three slots**, opened from the **States** button in the Files panel:

The DOS layer is in the snapshot as well, and that part is not a detail. A game that has `SOUND\MUSIC.FLX` open expects that file to still be open when it comes back. Without the handles in the snapshot, Ultima VIII walked into its own extender and aborted about a second after every restore, with `DOS Error=0006 (invalid handle)`. With them, the sixteen handles come back and the music keeps playing.

There is one more subtlety, and it is the difference between a snapshot that works and one that crashes the game. The snapshot has to be taken at a **safe point**: the guest program must actually be running, the picture must have settled, and the CPU must not be standing inside an interrupt stub with an `IRET` pending. Take it in the wrong place and you restore into the middle of a BIOS call — the kind of corruption that looks like a broken game rather than a broken save. So the request waits at three gates instead of firing at the first opportunity.

## A slot is a file on the phone

That is the other half of the idea, and it is the half that changes how you play. A slot is not a row in a database and not a blob in the app's memory: it is a **file on the phone**. So it survives quitting the app, and it survives rebooting the phone, and it survives updating the APK. The machine you froze is still there in the morning.

**Load** then jumps back to that exact moment. Under the hood this is not a button that copies a file. The app tears its own process down, boots a clean emulator with nothing queued, waits for the picture to settle, and only then restores the machine into it. A restore that happens a fraction of a second too early — while the phone is still rotating the screen — restores into a renderer that is about to be thrown away, and you get a black screen. I chased that one for a while too.

Every save and every load writes one summary line — the registers, the descriptor table and the top of the stack, with a checksum on each. The two lines have to be identical when a state comes back, because that is the proof that the restore brought *the* machine back and not merely something similar.

## Resume finally means resume

Two releases earlier I gave the launcher a **Resume** button. It looked like a promise: press it, and you are back in the game you were playing.

It was not. It started the last game from the beginning, every time. I did not notice it myself, because on my desk the emulator process was still alive — the game had never really stopped, so there was nothing to resume. Then somebody on a phone pressed the button, lost an hour of progress, and told me plainly: *the Resume button restarts the game.*

They were right. And the fix was not a one-liner; it was a whole-machine snapshot.

So the button now restores the newest save state of the last game you played, and it tells you what it is about to do — *Resume STARFALL · slot 1 · 5 min ago*. With no slot saved, the game starts from the beginning, exactly as before.

## Two smaller things in the same release

**The arrows are an inverted T.** In landscape the four arrow keys sit in the right-hand column the way they do on a real keyboard — up on top, left and right side by side, down below. The change is small and I am fond of it: the finger had to *know* which of the four was which before. Now the thumb reads the shape.

**The game keeps running.** While a game is running, a small ongoing notification holds the emulator process, so switching to another app no longer loses the game. Tap the notification and you come back to the same frame — no save, no reload.

## What a restore cannot do yet

**Some old DOS programs do not survive a restore.** Ultima VIII's extender still aborts about a second after the load, with `Exit to error: RET from illegal descriptor type 13`.

That is not the app, and it is not the Resume path: loading the same slot by hand, with the panel open, does exactly the same thing. What the snapshot does not capture yet is the rest of the host state a DOS/4GW game leans on — the DMA controller, the EMS and XMS handle tables and the PIC event queue. It is a limitation of the DOS internals the snapshot does not cover yet, not of the app, and the [technical reference](https://github.com/whereq/whereq-dosbox/blob/main/docs/TECHNICAL-REFERENCE.md) has the details.

The sound chips are not in the snapshot yet either. The machine comes back with its memory and its picture; the music does not come back with it.

Until it does: STARFALL saves and resumes perfectly, and a game like Ultima VIII can be saved and restored — but its extender does not like what it finds.

It runs on **arm64-v8a, armeabi-v7a and x86_64** devices, Android 5.0 and newer, entirely offline, with no account and no tracking. The project is GPL-2.0, and the DOSBox core is embedded with its `AUTHORS`, `ChangeLog`, `COPYING` and per-file headers intact.

## Thank you, DOSBox

None of this is possible without the DOSBox project.

**DOSBox** was written by the [DOSBox Team](https://www.dosbox.com/crew.php) — a volunteer crew who took an operating system from 1994 and made it runnable on every machine the world has produced since, including the ones that did not exist yet. They kept it alive for three decades and gave it away to anyone who wanted it. WhereQ-DOSBox is a thin layer on top of their work. The originality, the craft and the generosity are entirely theirs.

This port is built on **[Em-DOSBox](https://github.com/dreamlayers/em-dosbox)**, the Emscripten build of DOSBox r4305 by [Boris Gjenero](https://github.com/dreamlayers), which grew out of [Ismail Khatib's](https://github.com/CeRiAl) first attempt to compile DOSBox with Emscripten, and rode on the Emscripten work of [Alon Zakai](https://github.com/kripken/). The SDL2 library by [Sam Lantinga](https://github.com/libsdl-org/SDL) carries the window, the audio and the touch input.
