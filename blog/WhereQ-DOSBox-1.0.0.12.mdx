A save state is the one thing the emulator exists for. It is the whole machine, frozen — the CPU, the DOS memory, the video memory, the open file handles, the timers — so that you can come back to the exact moment you left.

Until this release, that frozen machine lived inside the app's own private storage. Android deletes that storage the moment the app is uninstalled.

So it happens the boring way. The phone is full, or the app starts misbehaving, or you simply decide to reinstall it. You install the APK again, the game bundle is still sitting in the folder you picked, you press **Play** — and the game starts at the very beginning.

Ten hours of progress, gone. Not because the game was lost. Because the app was.

And a phone that falls in the river takes the app with it, and the app takes the saves with it.

<!-- truncate -->

That was the truth about WhereQ-DOSBox until 1.0.0.12: the one thing the emulator exists to protect was the one thing that could not survive the app.

## The saves live outside the app now

The fix is not clever. It is that the saves stop living in a place Android is allowed to delete.

Pick a folder on the phone — **Config → Saves folder**, or the offer that appears after the first save — and every slot is mirrored there, gzipped, right next to the game itself:

```
  the app                          the folder you picked
  ──────                          ────────────────────
  the slot   ── gzip ──▶             STARFALL/
                                     slot1.gz
                                     slot2.gz
                                     bundle.zip      (the game)
```

Now the games are yours, in a folder you chose, and their save states are already there beside them.

And that folder is not a special place. It is an ordinary folder in the phone's storage: you can copy it, sync it, move it, put it on a cloud drive — the same way you would treat any other folder of files. One thing to know before you pick it: Android will not let an app take the **Download** folder itself, because that would be too broad a permission. Pick any other one — **Documents** is fine.

A reinstall, a new phone, an app deleted by accident. The games are offered for restore by name, with their save states already there beside them.

One detail worth knowing, because it is the kind of thing that quietly loses work: two archives with the same file name are told apart by name — *game* and *game (2)* — so their saves never end up in the same place.

## What a save state should remember

The second thing in this release is inside the save file, and it is about the mouse.

A DOS program does not just read the mouse. It *configures* it: it registers an event callback, sets the range the cursor may travel in, picks a cursor shape and the hotspot inside that shape, and decides how coarse and how sensitive the movement is. All of that is a property of the game, and the game will never send it again. So a save state has to carry it.

1.0.0.11 carried far too much. It put the *whole* INT 33h driver into the snapshot — the event queue, the click counters and the interrupt re-entrancy flags included. Restoring that wedged mouse-driven games: the stale queue and the stuck flags fed garbage into the interrupt handler and into the game's own callback, and a game could hang on load. The machine came back, but the mouse never reached the game again.

So the snapshot now carries the configuration the guest cannot rebuild itself, and leaves the run-time state out:

| in the save state | not in the save state |
|---|---|
| the game's event-callback registration | the queue of pending events |
| the cursor range and position | the click counters |
| the cursor shape and its hotspot | the interrupt re-entrancy flags |
| the granularity and the sensitivity | which buttons were held down |

The cursor shape matters as much as the rest. Without it the visible cursor reverts to the default block and stops lining up with the real click point, so your taps land beside the target instead of on it.

What a restore no longer carries is the state of the moment you saved. That belongs to the past, not to the machine you are coming back to. A restored game starts from an idle driver, with the mouse released — if you were holding a button down across the save, you press it again.

## Two things I want to say plainly

### Your old save states will not load

**Save states written by 1.0.0.11 and by the earlier 1.0.0.12 cuts cannot be loaded by this build.** The state file grew a version when the mouse block changed, and an older state is refused rather than misread. That is the honest behaviour — a state that is half understood is worse than a state that is refused — but it does mean those slots are gone.

### This release was re-cut

The tag still reads `v1.0.0.12`, but the file behind the download link is a *different build* than the one first published under that name. Its checksum is a different checksum, too. ## Thank you, DOSBox

None of this is possible without the DOSBox project.

**DOSBox** was written by the [DOSBox Team](https://www.dosbox.com/crew.php) — a volunteer crew who took an operating system from 1994 and made it runnable on every machine the world has produced since, including the ones that did not exist yet. They kept it alive for three decades and gave it away to anyone who wanted it. WhereQ-DOSBox is a thin layer on top of their work. The originality, the craft and the generosity are entirely theirs.

This port is built on **[Em-DOSBox](https://github.com/dreamlayers/em-dosbox)**, the Emscripten build of DOSBox r4305 by [Boris Gjenero](https://github.com/dreamlayers), which grew out of [Ismail Khatib's](https://github.com/CeRiAl) first attempt to compile DOSBox with Emscripten, and rode on the Emscripten work of [Alon Zakai](https://github.com/kripken/). The SDL2 library by [Sam Lantinga](https://github.com/libsdl-org/SDL) carries the window, the audio and the touch input.
