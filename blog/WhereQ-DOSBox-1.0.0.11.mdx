## The button you could not press

You are inside a game. You open a menu, and at the right end of the row of choices there is the way out — in most DOS games that way out is the right mouse button. *Cancel*. *Back*.

A DOS mouse had two buttons. Your phone has one finger, and no right button at all. So the game was complete and its exit was somewhere you could not reach.

That was 1.0.0.10, and every release before it.

## A mouse with two buttons, a screen with one

The on-screen keyboard now has an **RMB** key on the left pad, next to **Tab**. It is in all three layouts — the pads, the single key column and the bottom bar — so a right click is always one tap away.

And a **second finger** on the picture does the same, at that finger's own position. Put two fingers on the game and the second one is the right button, exactly where it is.

## A click is a press, not a tap

The first finger holds the **left** button for as long as it is down, so a drag is still a drag: the button was never released in the middle of it. The right button is held the same way.

This is what a game that reads the mouse *live* needs — the button state at `INT 33h AX=3`. A click that was over in a millisecond could fall between two polls and be missed altogether.

## The mouse was never in the save state

A save state freezes the whole machine: the CPU, the memory, the video memory, the sound chips. You save, you quit, you come back tomorrow, and you load.

Everything comes back. Except the mouse.

The `INT 33h` driver keeps its state outside the game's own memory — the event-callback registration, the cursor range, the button state. None of that was in the snapshot. So after a restore the cursor still moved, your finger still steered, and the game's clicks stopped reaching it: a dialog's *confirm* button did nothing at all.

The driver is now part of the state. It is saved with the machine and it comes back with it.

## One consequence you should know about

**Save states written by 1.0.0.10 cannot be loaded by this build.**

The state file grew a version when the mouse driver joined the snapshot, and an older state is refused rather than misread. That is the honest behaviour — a state that loads but plays wrong is worse than a state that says no.

If you have save states from 1.0.0.10 that you care about, load them before you update.

## The migration phase closed here

This release shipped the mouse work that closed the Android migration phase: the right button, the held click, and the driver going into the save state.

The marker is a tag that is not a release:

```
milestone/android-migration-complete
```

It is annotated, it rode on this release, and it deliberately sits outside the `vX.Y.Z` scheme the release script understands, so the script will never pick it up and try to release it again. It marks a phase, not a version. What comes after this is maintenance.

## Thank you, DOSBox

None of this is possible without the DOSBox project.

**DOSBox** was written by the [DOSBox Team](https://www.dosbox.com/crew.php) — a volunteer crew who took an operating system from 1994 and made it runnable on every machine the world has produced since, including the ones that did not exist yet. They kept it alive for three decades and gave it away to anyone who wanted it. WhereQ-DOSBox is a thin layer on top of their work. The originality, the craft and the generosity are entirely theirs.

This port is built on **[Em-DOSBox](https://github.com/dreamlayers/em-dosbox)**, the Emscripten build of DOSBox r4305 by [Boris Gjenero](https://github.com/dreamlayers), which grew out of [Ismail Khatib's](https://github.com/CeRiAl) first attempt to compile DOSBox with Emscripten, and rode on the Emscripten work of [Alon Zakai](https://github.com/kripken/). The SDL2 library by [Sam Lantinga](https://github.com/libsdl-org/SDL) carries the window, the audio and the touch input — the finger that becomes a mouse button included.
